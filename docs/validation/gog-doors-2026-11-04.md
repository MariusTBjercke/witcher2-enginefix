`witcher2.EXE+0x343F48` is `00743F48`, the return address of `call eax` in the CRT's

catch in this run either.)

## Seen in passing, not part of the port

With `load_trace=1`, `script patches: CreateFileW slot never held the kernel32 export - off` came
two minutes after the start. The load trace hooks `CreateFileW` first, with the same shared hook,
and the script-hook thread waits for the kernel32 export instead of accepting that hook. The
script archive was still redirected (`-> cached copy`), but the two `FindFirstFileW`/
`FindNextFileW` hooks were not installed. The same line is in Steam logs from 2026-11-02 with
`load_trace=1`, so it is not GOG-specific.

## Steam, the same build (regression check)

Steam 3.5.0.26 with DXVK and the owner's own ini. The same working build, which also contains
the door-transitions changes (`docs/fixes/door-transitions.md`). The owner went through the
inn's door and Einar Gausel's door in Flotsam, both ways, and quit through the pause menu
(13:53-13:55). The Steam paths the GOG port touched behave as before:

```text
build: Steam 3.5.0.26 (TimeDateStamp 518B881C, .text 008A94AD), delta 0x00000000 from 0x00400000; import slots 27/27 found by name
exit: hooked kernel32.dll!GetProcAddress
exit (steam_api.dll): hooked kernel32.dll!ExitProcess
doors: fade-out patched, fade-in patched, 0.05 s, area changes 0.25 s (game 0.5 s); fast_doors=1
doors: 'Outdoor\global\landing_site\outside\Flotsam' -> 'Outdoor\global\landing_site\outside\inn_interior' is loaded - no fade (7 to load)
doors: interior ready after 78 ms - picture back now (state 2)
doors: Geralt is through the door - loading the occluders (4016 ms after the door)
...
exit: ExitProcess(0) from witcher2.EXE+0x272388 on thread 3116 (the main thread)
unloaded
```

- **Partition request.** The stub now sets EAX and ECX to the game and calls through EDX. The
  occluders still load.
- **CName lookup.** It now checks its first bytes before the call. The `fade_out` handler still
  takes the DLL's event (`state 2`).
- **Exit.** On Steam the CRT calls `ExitProcess` directly (`witcher2.EXE+0x272388` is right after
  `call [ExitProcess]` in `__crtExitProcess`). The DLL detach follows.

In a second Steam run the owner loaded a save made inside the inn, in the same process. Later
some ceilings and roofs showed corrupted textures (blue and green pixel garbage). That run went
through `preload_street`, new in the door-transitions change; it is followed up there.

After this test, the `GetProcAddress` hook became a tail jump, so every lookup other than
`CorExitProcess` reaches Windows with the game's own return address. `tools/buildprobe` calls it
directly. Start test on 2026-11-04 at 14:08-14:09, Continue then Quit on both installs:
GOG ended with `exit: CorExitProcess(0) from witcher2.EXE+0x343F48`, and Steam with
`exit: ExitProcess(0) from witcher2.EXE+0x272388` followed by `unloaded`. Every door hook went in
on both, and there was no dump.
